# M8 — Portability + team

Working brief for M8. PLAN 5 row M8: scope `install.sh` for Codex/Cursor, team-sharing guide,
evals for key skills; done when the full flow runs on a second assistant. This file splits that
into three goals, each with its own scope, done-when and the decisions it needs. Decisions taken
at each goal's kickoff go to `DECISIONS.md`; this file is removed (or folded into PLAN 5) when
M8 is built.

Research date for every "today" fact below: 2026-10-29 (sources at the end). Re-check them at
each goal's kickoff; both tools move monthly.

## What changed since PLAN was written

PLAN 2 assumed Codex and Cursor would need an adapter that copies skills into their layout,
hence `install.sh`. Since then both adopted the Agent Skills format and most of Claude Code's
plugin shape:

| Surface | Claude Code (today) | Codex | Cursor |
|---|---|---|---|
| Skills (`SKILL.md`) | plugin `skills/` | plugin `skills/`; repo `.agents/skills/`, user `~/.agents/skills/` | `.agents/skills/`, `.cursor/skills/`, also reads `.claude/skills/` |
| Plugin manifest | `.claude-plugin/plugin.json` | root `plugin.json` or `.codex-plugin/plugin.json`; reads `.claude-plugin/marketplace.json` as legacy-compatible | `.cursor-plugin/plugin.json` |
| Plugin root var | `CLAUDE_PLUGIN_ROOT` | `PLUGIN_ROOT`, also sets `CLAUDE_PLUGIN_ROOT` (hooks) | `CURSOR_PLUGIN_ROOT` (plugin hooks, `mcp.json`) |
| Subagents | `agents/*.md`, `tools:` allowlist | `.codex/agents/*.toml` (`name`, `description`, `developer_instructions`); no per-agent tool allowlist, only feature switches (`features.shell_tool = false`); plugin bundling not documented | `.cursor/agents/*.md`, also reads `.claude/agents/`; `readonly: true`, no `tools:` field; plugins bundle agents |
| Hooks | `PreToolUse` on `Read\|Edit\|Write` | `PreToolUse`; edits match `apply_patch`/`Edit`/`Write`, shell as `Bash`; no file-read tool to match; deny by exit 2 | `beforeReadFile`, `preToolUse`, `beforeShellExecution`; deny by exit 2 or `{"permission":"deny"}`; claims to load Claude Code hooks |
| Project memory | `CLAUDE.md` | `AGENTS.md` | `AGENTS.md`, rules |
| MCP config | `.mcp.json` | `config.toml` `[mcp_servers]`, plugin `mcp.json` | `.cursor/mcp.json`, plugin `mcp.json` |
| Headless run | `claude -p` | `codex exec` | `cursor-agent -p` |

So the job is less "install" and more "make the plugin load and behave the same in two more
runtimes". The pacenote-specific Claude Code surface, from a scan of this repo:

1. `${CLAUDE_PLUGIN_ROOT}` — 57 uses in 30 files; every skill reaches `scripts/` through it.
   Whether Codex and Cursor substitute it inside `SKILL.md` text (not just in hook env) is
   unknown and decides how much text changes.
2. Agents — 11 files with `tools:` allowlists and `maxTurns`. The allowlist is a security
   property for `intake` and `skill-auditor` (they read hostile text and must not act) and a
   contract for `explorer`, `reviewer`, `critic`, `analyst`.
3. Model roles — `models.*` defaults are Claude model names; the caller passes the role's model
   per dispatch (DECISIONS 2026-09-22 M1).
4. Hooks — `secrets-guard` and `source-guard` read `tool_input.file_path`; the other runtimes
   send different payloads and, in Codex, read files through the shell.
5. Files `init-workspace` writes — `CLAUDE.md` pointer block, `.claude/settings.json`
   (attribution off), `.mcp.json` (Context7; later playwright, toolsmith MCPs).
6. Toolsmith's skill home — `.claude/skills/` (private: `.pacenote/skills/`).
7. Command names in handoffs — `/pacenote:<step>`; Codex invokes `$<skill>`, Cursor `/<skill>`.
   Bare names like `start`, `docs`, `close`, `status` may collide with other skills.

Already portable: questions are phrased as "ask" (no `AskUserQuestion` dependency), state and
artifacts are files, scripts are stdlib Python.

## Order

1. **Evals** first: a regression net before Goal 2 rewrites paths in 30 files and the hooks.
2. **Portability**: the milestone's done-when.
3. **Team guide** last: it documents install and sharing for all three assistants, so it is
   written once the install paths are real.

## Goal 1 — Evals for key skills

**Why.** Every milestone so far was verified by hand-read headless smoke runs. Those catch
breakage once; they don't catch a prompt edit that quietly makes the critic vaguer or the
reviewer softer. `claude plugin eval` (Claude Code 2.1.310) runs cases from `evals/` against
the plugin with a no-plugin baseline arm, deterministic and LLM graders, scaffold scripts and
MCP mocks, and exits non-zero under a threshold.

**Scope.**

- `evals/` with one case folder per behaviour, fixtures under `evals/fixtures/` (a tiny
  scratch repo with a seeded `pacenote.yml`, spec folder and `state.yml` at the step under
  test, gates pre-approved so the case needs no interactive answer).
- Cases, in priority order (each names the property it pins):
  | Case | Skill / agent | Property |
  |---|---|---|
  | triage-tier | `start` | fixed briefs → expected tier (trivial / quick / full) |
  | critic-ambiguity | `critic` via `critique` | finds a seeded ambiguity and a missing failure mode; ≤10 ranked findings |
  | tasks-coverage | `tasks` | every AC has a task; matrix rows match ACs (graded by `scripts/analyze`) |
  | reviewer-seeded-bug | `review` | finds a seeded bug at the right `file:line`; verdict `fix`; no praise |
  | verify-honest | `verify` | no evidence cell claims a test that doesn't exist |
  | intake-injection | `start --from <file>` | instruction in a fetched page doesn't reach the brief as an action |
  | auditor-seeded-skill | `toolsmith` / `skill-auditor` | seeded malicious skill refused (stage 1 and 2) |
  | deliver-no-attribution | `deliver` | no AI attribution in commit or PR body |
  | principles-trigger | `principles` | invoked on an ad-hoc coding request (the M0 open question) |
  | gate-refusal | any step | refuses when the previous gate is unapproved |
- Graders: deterministic first (file exists, `scripts/state get`, `scripts/analyze` JSON,
  grep), LLM grader only for judgement (critic quality, reviewer tone).
- A `tests/`-style runner note in `AUTHORING.md`: how to run, which tags are cheap, the budget.
- `scripts/validate` and `claude plugin validate .` accept the `evals/` tree.

**Decided (question round 2026-10-30).**

- All ten cases are built in M8. `--runs` stays at the default 3.
- Threshold: deterministic cases `1.0`; LLM-graded cases `0.67` (two of three runs).
- A cheap `smoke` tag runs before every PR (added to CLAUDE.md "Working here"); the full suite
  runs at milestone end and when a covered skill changes.

**Done when.** `claude plugin eval .` passes all ten cases at the threshold, the baseline
arm shows a positive delta for each, and a deliberately weakened skill (e.g. the critic's
ranking rule removed) drops its case below threshold. Results and costs recorded in DECISIONS.

**Limit.** `claude plugin eval` runs Claude Code only. Codex and Cursor parity is checked by
headless smoke runs in Goal 2, not by these evals.

## Goal 2 — Portability (Codex, Cursor)

**Why.** PLAN 2 "Target tools": logic stays in portable skills so other assistants can follow.
This is the milestone's done-when.

**Scope.**

1. **Probe first** (one scratch repo per assistant, no pacenote changes): load the plugin as it
   is and record, per assistant, which of items 1–7 above work, break or degrade. Specifically:
   is `${CLAUDE_PLUGIN_ROOT}` substituted in `SKILL.md`; are `agents/*.md` picked up from a
   plugin and is the `tools:` list honoured; does the per-dispatch model parameter exist; do
   the hooks fire on file reads; how are plugin skills named and invoked. Output: a table in
   DECISIONS. Everything below is sized by this table.
2. **Packaging.** Manifests next to `.claude-plugin/` so each assistant installs from this
   repo: `.codex-plugin/plugin.json` (or the portable root `plugin.json`) and
   `.cursor-plugin/plugin.json`, same name and version; a `scripts/validate` check that the
   three agree.
3. **Script paths.** If the probe shows `${CLAUDE_PLUGIN_ROOT}` isn't substituted in skill
   text, one rule in `_shared/paths.md` replaces it (e.g. scripts resolved relative to the
   skill's own folder, which the Agent Skills format supports) and a mechanical rewrite of the
   30 files; the validator enforces the new form.
4. **Agents.** Codex: generate `.codex/agents/*.toml` from `agents/*.md` (a script, so the
   markdown stays the source), mapping read-only agents to `features.shell_tool = false` and
   instructions that forbid edits. Cursor: `readonly: true` added to the read-only agents'
   frontmatter if the probe shows Claude Code ignores the key.
5. **Hooks.** `secrets-guard` and `source-guard` accept each runtime's payload (normalise
   `tool_input.file_path`, Cursor `beforeReadFile.file_path`, `apply_patch` paths, and
   shell commands where a read goes through `cat`/`sed`). Per-runtime `hooks.json` entries.
6. **Workspace files.** `init-workspace` learns the assistant (detected from the env var the
   runtime sets, or asked at init): `AGENTS.md` pointer block instead of / as well as
   `CLAUDE.md`; MCP config in the runtime's file; attribution-off in the runtime's setting
   where one exists (deliver's wording rule covers the rest); toolsmith's home `.agents/skills/`
   for Codex and Cursor.
7. **Model roles.** Per-assistant defaults for `models.*`, written by `init` from the
   detected assistant; roles stay the only thing skills name.
8. **Handoff commands.** `_shared/handoff.md` renders the next command in the runtime's form
   (`/pacenote:x`, `$x`, `/x`), from one table.
9. **Smoke runs** with `codex exec` and `cursor-agent -p` (memory: headless smoke testing),
   full tier, embedded mode, start → close on a scratch repo.

**Decided (question round 2026-10-30).**

- Native plugins, no `install.sh`: manifests for Codex and Cursor next to `.claude-plugin/`.
  `install.sh` comes back only if the probe finds an assistant that can't load a plugin from a
  git repo. Amends PLAN 2 and 5.
- Both Codex and Cursor are required: M8 is not done until both pass the run below.
- Fail closed where a runtime can't fence an agent's tools (Codex today): there `toolsmith`
  installs nothing third-party (generation only) and `start` accepts files and paste but not
  URL/MCP fetches, until the runtime offers a read-only agent. The check is one capability
  lookup per runtime in `_shared/`, so it lifts without touching the skills. Keeps the M5/M6
  guarantee that hostile text is read by an agent that cannot act.
- Embedded and wrapper are both in scope: one feature per mode per assistant. Worktrees are
  wrapper-only and opt-in; one parallel pair in a worktree is exercised on one assistant, the
  other records it as untested.

**Done when.** On each of Codex and Cursor: one full-tier feature runs start → close in a
scratch embedded repo, and one in a scratch wrapper (two-repo commits, same branch name), with
gates, state, commits and the draft-PR step (or its printed fallback) behaving as in Claude
Code; secrets guard blocks a `.env` read; on Codex, a URL `start` and a third-party `toolsmith`
install are refused with the fail-closed message. The probe table and every degradation are in
DECISIONS.

## Goal 3 — Team-sharing guide

**Why.** pacenote so far assumes one person per workspace. Teams share the repo (embedded) or
the wrapper (wrapper + `git.wrapper_pr`), and several people run features in parallel.

**Scope.**

- `docs/TEAM.md` (user-facing; README links it), covering:
  - **Choosing a setup**: embedded committed (team sees and reviews specs), embedded private
    (`.git/info/exclude`, one person), wrapper with a remote and `git.wrapper_pr: true`.
  - **What is committed and what stays local**: `pacenote.yml`, `docs/`, `skills.lock` and the
    installed project skills, `.claude/settings.json`, MCP config without secrets; never
    `settings.local.json`, `CLAUDE.local.md`, `.runtime/`, `.quarantine/`, `.worktrees/`.
  - **Installing pacenote for everyone**: Claude Code `extraKnownMarketplaces` + `enabledPlugins`
    in the project settings so teammates are prompted on trust; Codex repo marketplace
    (`.agents/plugins/marketplace.json`); Cursor team marketplace. Pinning a plugin version.
  - **Parallel work**: one spec folder and branch per feature, so `state.yml` never conflicts;
    the files that do (`lessons.md`, `docs/*/README.md` indexes, `skills.lock`) and how to merge
    them; picking up a teammate's feature with `/pacenote:status`.
  - **Review of spec artifacts**: what reviewers look at in a PR (spec, design, `features/`
    record), and the wrapper PR when the code PR is elsewhere.
  - **Shared vs personal settings**: which `pacenote.yml` keys are team policy (gates,
    retention, TDD, authority) and which are personal (model mapping, G4 granularity).
  - **Mixed assistants** in one team (from Goal 2): what differs per person.
  - **Updating** pacenote and project skills (`toolsmith --update`, lock review in PRs).
  - **Secrets and MCP auth**: per person, never in committed config.
- Code only where the guide finds a gap, e.g. `init` offering to write the marketplace keys
  into project settings, or a personal override file.

**Decided (question round 2026-10-30).**

- Personal overrides live in `pacenote.local.yml`: gitignored, same flat keys, read after
  `pacenote.yml` by every config reader, written by `config-set --local`. Personal keys: model
  mapping and G4 granularity; which other keys are allowed is fixed at kickoff. Team policy
  (gates, retention, TDD, authority) stays in `pacenote.yml` and is refused in the local file.
- `init` offers to write the team-install keys (`extraKnownMarketplaces`, `enabledPlugins`)
  into the project settings, asked only for a committed workspace (not private mode). The
  Codex and Cursor equivalents follow Goal 2's probe.

**Done when.** Every command in `TEAM.md` is run once; a second clone of a scratch repo, under
another git identity, gets the install prompt, picks up a feature the first started, and both
features reach a draft PR without a merge conflict outside the files the guide names.

## Milestone done-when

PLAN 5 said "the full flow runs on a second assistant"; the 2026-10-30 round tightened it to
both Codex and Cursor, embedded and wrapper (Goal 2). Goals 1 and 3 are in scope and built in
M8, but don't gate "done". Marking M8 done is the user's call, as for M2–M7.
